# 踩过的坑

这个项目是跟 Claude Code 一路结对写下来的，过程里犯过几个不算小的错，记下来给别人（也给未来的自己）参考。不是"最佳实践清单"，就是几次具体的、代价不小的教训。

## 1. 一个肉眼看不见的字符，让心情标记全库失效了一整个版本周期

**症状**：手机上导入 PC 端批量生成的 `mood_labels.json`，导入提示成功，但 Library 里一首歌的分类都没变，Home 的激情/平静 tile 点开显示"这个分类下还没有歌"。手动在 App 里长按标记单独一首歌，导出后再导入，那首歌也丢了。

**排查走过的弯路**：
- 一开始怀疑是 Navidrome 没重新扫描库、服务器上文件还是老标签——合理怀疑，但排除后没用。
- 然后怀疑是 CoroutineScope 生命周期问题（长按标记的写入协程挂在 Library 页面的 `rememberCoroutineScope()` 上，如果标记完立刻切到别的 tab，协程可能被取消，DataStore 的写入还没落盘就被打断）——这个猜测**后来证明也是真实存在的一个 bug**，顺手用 `withContext(NonCancellable)` 包住了关键写入，但它不是这次问题的主因。
- 用 adb 直接把手机上 DataStore 的 protobuf 文件 `run-as` 导出来看，第一次看完全是乱码——因为 **PowerShell 的 `>` 重定向会用文本编码方式转手外部程序的二进制输出，把二进制数据搞坏**。换成 `cmd /c "adb.exe ... > file"` 才拿到没被污染的原始字节，这是第二个独立的坑（见下一条）。
- 拿到干净的数据后发现 JSON 本身是合法、完整的 711 条记录——数据没问题，说明是"读取时怎么匹配"的问题。
- 加了一行临时 debug log 打印某首歌算出来的 key 长度：预期 `"After I Pass Away" + "Mikhail Bennett"` = 32 个字符，日志显示是 **33**。多出来的这一个字符，就是线索。
- 最后直接 dump 源代码那一行的字符编码（`Get-Content ... | ToCharArray() | %{ [int]$_ }`），才看到 `${song.title}` 和 `${song.artist}` 两个字符串插值中间，赫然混进了一个字节值为 `1`（SOH 控制字符）的字符——**在 `Read` 工具、在编辑器里，这个字符完全不显示，看起来就是干净的字符串拼接**。

**根因**：源代码文件本身在某次编辑中混入了一个不可见控制字符，导致编译出来的 key 计算函数实际上是 `title + "" + artist`，跟 PC 端 Python 脚本生成的干净 key（`title + artist`）永远对不上。

**教训**：
- 如果一段代码"看起来"完全正常，但行为却像是有细微差异，别急着怀疑逻辑本身——先怀疑数据本身有你看不见的东西。
- **`Edit` 工具的字符串精确匹配失败，且反复用 `Read` 核对过文本"看起来完全一样"，这本身就是一个强信号**：很可能是不可见字符在捣鬼，去 dump 字符编码，不要归咎于工具抽风。
- 处理任何"跨系统/跨语言比较字符串是否相等"的场景（本例是 Kotlin 算出来的 key vs. Python 算出来的 key），只要输入数据来源不完全干净（这里是历史上处理过的、来源混乱的 MP3 标签），最好在两边都做一次标准化清洗，而不是假设"看起来一样就真的一样"。

## 2. 诊断工具本身的 bug，一度让人怀疑错了方向

在上面这条排查过程里，写了个小脚本从 protobuf 二进制里"抠出" `mood_labels` 那段 JSON 来验证是否合法——第一版用简单粗暴的"找最后一个 `}`"，结果把后面紧跟着的另一个字段（`playback_state`，同样是 JSON，也以 `}` 结尾）一起截了进去，两段 JSON 粘一起，解析当然失败，一度让人以为"数据本身就是坏的"。

**教训**：写诊断/校验脚本时，脚本本身的 bug 和被诊断对象的 bug 长得一模一样（都是"结果不对"）。发现"数据损坏"之类的结论时，先怀疑自己的检测逻辑是否够严谨（这里的正确做法是做括号配对计数，而不是找最后一个字符）。

## 3. `moodKey` 用"标题+艺人"字符串拼接做 key，代价是脆弱

设计本身是合理的（不依赖文件路径/服务器 ID，文件换了内容会安全变回"未分类"，见 [`SongRepository.kt`](../app/src/main/java/com/example/music/data/SongRepository.kt)），但字符串拼接对"两边数据源必须完全一致"这件事非常敏感——上面第 1 条就是代价。如果重新设计，会考虑在拼接前统一做一次标准化（去除首尾空白、折叠不可见字符），而不是假设两边的原始字符串本来就该完全相等。

## 4. CoroutineScope 绑定到屏幕生命周期，用来做"必须完成"的写入是危险的

Library 页面长按标记心情、点收藏，原来的写法是 `scope.launch { SongRepository.setMoodLabel(...) }`，`scope` 是 `rememberCoroutineScope()`——绑定的是这个 Composable 的生命周期。如果标记完立刻切到别的 Tab，Library 被踢出 composition，这个 scope 会被取消，如果此时 DataStore 的 `edit {}` 事务还没提交完，写入就会被从中打断，数据不落盘。

**修复**：把这类"一旦开始就必须做完"的持久化操作，用 `withContext(NonCancellable) { ... }` 包起来，保证外层协程被取消也不会打断这段关键逻辑。

**教训**：任何写入操作，只要不是纯粹"这个屏幕存在的时候才有意义"的（比如动画状态），只要它涉及到落盘持久化，就该考虑它的协程作用域是否会在写入完成前被意外取消。

## 5. 用 debug 版 apk + `adb run-as` 可以在不 root 的手机上查看 App 私有数据

不是 bug，是这个项目里学到的一个好用技巧，记一下：Android 的 `/data/data/<package>/` 目录默认需要 root 才能访问，但如果 App 是 **debuggable**（debug 编译出来的都是），可以不用 root，直接：

```bash
adb shell run-as com.example.music ls -la files/datastore/
adb exec-out run-as com.example.music cat files/datastore/settings.preferences_pb > dump.bin
```

（`exec-out` 而不是 `shell`，且如果在 Windows PowerShell 里跑，外面套一层 `cmd /c "..."`，见坑 1——PowerShell 原生的 `>` 会污染二进制流。）

## 6. "播放模式"切换按钮，只在下一次开始播放时生效，不会改变已经在放的队列

Home 点激情/平静/随机时，代码里无脑对筛选结果做了一次 `.shuffled()`，跟"顺序播放/随机播放"那个模式切换开关完全没有关联——用户切成"顺序播放"之后，新点开的分类确实是乱序的，因为这个逻辑压根没看当前模式是什么。

更隐蔽的是第二层 bug：即使把"是否要洗牌"这件事接上了播放模式开关，切换开关本身也**只会影响下一次新建队列，或者队列循环回到开头**——已经在播放中的这个队列，剩下没播的部分不会跟着重排,给人一种"这个开关根本没用"的错觉。

**教训**：一个"模式"类的开关，如果用户切换它时界面上视觉上什么都没变，会被当成没生效——即使它在逻辑上"下次会生效"。凡是有明显、即时视觉反馈预期的控件，该在切换的那一刻就把已存在的状态重新计算一遍，而不是等下一次自然触发的时机。

---

如果你在读这份文档是因为遇到了类似的诡异 bug：先怀疑数据，再怀疑自己的诊断工具，最后才怀疑"看起来正常"的代码逻辑本身。
